# 能力模型与成长阶段

**面对变化和复杂约束，持续解决有价值的问题，并将经验用于新的场景。** 这是本模型的顶层结论。技术路线提供训练材料，能力模型用于选择当前要承担的任务，以及判断结果的依据。

模型按“顶层结论 → 支撑结论 → 子能力”组织；成长表采用开发工程师、技术骨干、架构师三个角色，每个交叉单元用一句自我追问表达思考重点。岗位名称表示本计划中的责任视角，不直接对应统一公司的职级或年限。

## 一 能力金字塔

```text
顶层结论：面对变化和复杂约束，持续解决有价值的问题，并将经验用于新的场景
│
├─ 问题描述准确
│  ├─ 澄清目标与边界
│  └─ 表达状态与关系
├─ 原因判断可信
│  ├─ 获取并核对信息
│  └─ 提出并检验解释
├─ 方案选择合理
│  ├─ 构造可行方案
│  └─ 比较并作出取舍
└─ 实际结果兑现
   ├─ 实现与协同推进
   └─ 验收、复盘与复用
```

纵向检查下层是否足以支持上层：画出调用关系，还要有证据支持对原因的判断；完成发布，还要有实际结果支持“问题已经解决”。案例、代码和运行记录放在各项子能力下面作为验收材料。

横向按评价对象分组：**问题描述、原因判断、方案选择、实际效果**。推理验证检查解释是否成立，交付验收检查改完是否达标；同一次实验可以为不同评价对象提供证据。MECE 用于检查这些分类的重复与遗漏，具体工作中的思考和行动会共同使用多项子能力。

## 二 三个角色的责任与技术边界

开发工程师关注“怎样把功能做对”，技术骨干关注“现成办法不够用时，怎样解决关键问题”，架构师关注“什么值得做，怎样投入和持续演进”。

| 角色 | 主要承担什么 | 技术边界 |
| --- | --- | --- |
| 开发工程师 | 在既定业务目标和架构内，实现完整功能并持续维护负责部分 | 读懂并修改业务代码，贯通接口、数据、权限、本地事务与下游调用，完成调试和验证 |
| 技术骨干 | 解决关键技术难题，形成满足系统约束的方案并推动实施 | 根据问题深入运行机制、并发、数据一致性、容量或分布式计算，处理机制交互与故障恢复 |
| 架构师 | 根据业务目标判断技术投入，确定系统边界与演进路径并检验长期效果 | 对关键技术保证和可替换性作判断，结合业务差异、成本、团队能力和迁移风险安排演进 |

技术边界表示能够解释、修改并承担后果的范围，具体组件按业务选择。一个关键模块也可能有很深的技术难题；技术骨干的作用可以通过技术判断和协作体现，不以管理权限为前提。同一个人也可能在不同任务中承担不同角色。

## 三 子能力与角色成长表

保留八项子能力的名称，每格只表达该角色主要负责回答的问题。三个角色共享基础方法，差异通过任务条件、判断责任和结果范围观察。

| 支撑结论 | 子能力 | 开发工程师 | 技术骨干 | 架构师 |
| --- | --- | --- | --- | --- |
| 问题描述准确 | **澄清目标与边界** | 这个功能要达到什么效果，哪些情况算失败？ | 多方要求冲突时，系统必须优先保证什么？ | 哪个业务问题值得技术投入，先解决哪一个？ |
| 问题描述准确 | **表达状态与关系** | 这个功能涉及哪些数据和状态，它们怎样变化？ | 模块之间怎样分工，数据和规则到底由谁负责？ | 哪些业务能力应该共用，哪些差异需要保留，边界怎样随业务变化？ |
| 原因判断可信 | **获取并核对信息** | 实现和排错需要哪些资料、日志和数据，哪里还没弄懂？ | 现有证据缺了什么，互相矛盾的信息该怎样核实？ | 业务需求、技术判断和成本预估，分别有什么事实依据？ |
| 原因判断可信 | **提出并检验解释** | 这个故障为什么发生，修复是否有效？ | 多个模块各自正常，为什么组合后仍会出错？ | 这条技术路线凭什么能支撑业务，投入前先验证什么？ |
| 方案选择合理 | **构造可行方案** | 怎样在现有架构内，把正常和异常流程都实现完整？ | 在不能停机、资源有限等约束下，怎样给出可以实施的系统方案？ | 保留、整合还是替换现有能力，怎样分步演进并控制迁移风险？ |
| 方案选择合理 | **比较并作出取舍** | 哪种实现满足需求，又容易维护？ | 性能、可靠性、成本和交付时间冲突时，怎样选择？ | 人力和预算应该投向哪里，何时继续、暂缓或退出？ |
| 实际结果兑现 | **实现与协同推进** | 怎样完成开发、联调和上线，并处理自己负责功能的问题？ | 怎样协调依赖和改动顺序，让关键方案稳妥地落地？ | 怎样让相关团队对方向和责任达成一致，并持续采用和演进方案？ |
| 实际结果兑现 | **验收、复盘与复用** | 功能真的达标了吗，同类问题下次能否独立解决？ | 改进对整体是否有效，故障能否恢复，换个场景还能否复用？ | 业务收益是否兑现，实际成本是否符合预期，什么信号意味着需要调整方向？ |

快速学习与迁移贯穿每一行：进入陌生技术或业务后，能否补齐知识、验证理解，并再次取得可靠结果。每次补充三个观察：原本不会什么，怎样学会并验证，换个场景后是否还能独立使用。

## 四 用案例训练与验证

### 1. 沿完整解决链路收集证据

**发现问题 → 分析判断 → 实施 → 验证结果。** 这条链路用于组织任务；输入、处理、输出、反馈帮助检查信息和结果怎样流转。它们是工作流程索引，各环节都会使用金字塔中的多项子能力。

以下账户权限场景为通用训练假设，不描述某个公司的实际事故。

| 角色 | 面对的场景 | 从问题出现到解决的完整链路 |
| --- | --- | --- |
| 开发工程师 | 用户访问部分项目被拒，需要在既定架构内查明并修复 | 澄清谁应该有权 → 整理用户、项目、凭据状态 → 对照请求、日志和数据 → 提出并验证原因 → 实现兼容修复 → 回归、发布与回退 → 检查是否复发 |
| 技术骨干 | 权限变更在不同入口生效不一致，局部补丁不断增加 | 明确不可接受的结果 → 还原权威数据、缓存与信任边界 → 检验相互竞争的解释 → 比较机制调整方案 → 验证关键假设 → 协调渐进实施 → 验证整体效果、故障与恢复 |
| 架构师 | 多产品希望统一身份能力，同时存在权限差异、历史客户和预算约束 | 核实业务目标及当前成本 → 判断哪些共享、哪些保留差异 → 比较保留、整合与替换 → 验证关键假设 → 安排职责和迁移顺序 → 推动采用 → 持续核对收益、可靠性与成本 |

源码阅读形成问题模型和原因判断的证据；实现、运行和失败场景用于证明结果兑现。只完成明确的小改动时，按实际承担的范围记录，不据此认定已经具备整个角色要求。

### 3. 每轮保留结果和学习记录

| 记录项 | 填写内容 |
| --- | --- |
| 能力目标 | 当前承担哪种责任，重点训练哪一两项子能力 |
| 问题与预测 | 用户结果、规则、约束、未知点及自己对结果的预测 |
| 行动与决策 | 实际做了什么，如何补齐知识，比较了什么，哪些部分得到指导 |
| 结果与证据 | 正常、边界和失败结果，实际运行、恢复与测量记录 |
| 复盘与迁移 | 哪个判断得到修正，什么条件下可以复用，在新场景中怎样再次验证 |

每个目标记录“待验证 / 在指导下完成 / 独立完成 / 已跨场景迁移”，并附证据和实际责任范围。需求沟通、接口设计、调试和交付经验可以从前端迁移；服务端状态、事务、并发、网络失败和运行保障则继续用后端任务补证据。

面对商业或 AI 等新领域，也先明确当前任务需要什么，补齐相关知识，再用小范围实践检验收益、成本与风险。知识和工具持续更新，学习与迁移通过实际任务的重复验证体现。
