# 系统设计典型案例

## 技能迁移表

| 前端已有经验 | 后端对应能力 | 需要补上的差异 |
| --- | --- | --- |
| 把模糊需求变成页面行为 | 把目标变成功能、约束和验收 | 同时规定数据正确性、规模和失败后的结果 |
| 页面模块与状态归属 | 服务职责与数据所有权 | 跨进程后有网络失败和独立提交 |
| 请求耗时与前端性能测量 | 服务目标、吞吐和资源容量 | 同时观察排队、完成时间、错误和恢复能力 |
| 防抖、取消、重试交互 | 幂等、状态转换与恢复 | 必须在服务端持久化并承受多实例竞争 |
| 灰度、回滚与问题反馈 | 发布兼容、观测和方案演进 | 数据迁移和已经发生的副作用也要处理 |

本篇先逐个定义设计所需概念，最后设计一个文件导出服务。所有流量、文件大小和目标都是练习假设，不是公司平台实测值。

当前学习范围：把容量和故障实验当作有明确输入的设计训练；当前优先完成可交付功能，有测量之后再推导优化和架构方案。

## 一 需求先写成可以观察的行为

“支持导出”还不足以决定设计。先给一项操作补齐输入、结果和约束：

| 项目 | 最小例子 |
| --- | --- |
| 用户动作 | 项目成员提交筛选条件，导出订单 |
| 输入 | 项目、日期范围、字段列表 |
| 最终结果 | 得到一个可下载文件 |
| 时间要求 | 提交后很快得到受理结果，文件稍后生成 |
| 权限要求 | 只能导出并下载当前有权限的数据 |

对应到接口，可以先约定：

```http
POST /exports
Content-Type: application/json

{"projectId":"7","date":"2026-10-26"}
```

预期受理响应：

```http
HTTP/1.1 202 Accepted
Content-Type: application/json

{"taskId":"501","status":"QUEUED"}
```

202 在这里表示已受理，不代表文件已经生成。前端可以展示“正在生成”，再查询任务状态；后端必须先可靠记录任务，才返回受理成功。

还需要决定导出采用哪个时间的数据。本练习允许读取生成时的数据；若要求提交时的一致快照，需要额外的数据版本或快照能力，不能只保存一个时间字段就宣称实现。

## 二 业务不变量定义哪些结果不能发生

不变量就是无论重试、并发或进程重启，仍必须成立的业务规则。先写规则，再选技术：

| 规则 | 会违反它的最小场景 |
| --- | --- |
| 同一业务申请只有一个可见成功结果 | 用户重试后出现两份分别计费的结果 |
| 其他租户不能下载文件 | 把 taskId 从 501 改为另一个租户的编号 |
| 任务状态不能被旧执行者倒退 | 新执行已成功，旧执行却把状态改为失败 |
| 过期文件不能继续作为有效结果返回 | 元数据仍为成功，文件已被清理 |

任务可以先用这个状态模型表达：

```text
QUEUED → RUNNING → SUCCEEDED
                → FAILED
QUEUED → CANCELLED
SUCCEEDED → EXPIRED
```

每个转换都要定义发起者与前置条件。运行中的取消涉及实际执行是否已停止，可增加 CANCEL_REQUESTED 状态，不把前端关闭弹窗视为任务已取消。

## 三 服务目标需要定义测量口径

SLI 是实际测量出来的表现，SLO 是希望它达到的目标。先区分接口响应与业务完成：

| 观察对象 | 测量什么 | 本练习目标 |
| --- | --- | --- |
| 提交接口 | 合法申请中，2 秒内可靠受理的比例 | 99% |
| 导出任务 | 已受理任务中，120 秒内完成的比例 | 95% |
| 查询接口 | 测试流量下的响应时间分布 | p95 不超过 300ms |

这些目标还要约定观察窗口、失败口径、数据大小和允许负载。用户取消、权限拒绝、系统错误是否计入分母，也应明确。

举一个延迟计算例子：20 次查询中，19 次耗时 100ms，1 次耗时 1000ms。

```text
平均值 = (19 × 100 + 1 × 1000) / 20 = 145ms
```

本例按“排序后第 ceil(0.95×N) 个值”计算 p95，结果是第 19 个值，即 100ms。平均值和分位数描述的内容不同，最慢一次也仍需调查；实际监控系统的计算方式需要单独核对。[服务目标](https://sre.google/sre-book/service-level-objectives/)

## 四 容量估算先写单位与假设

### 1. 到达速度与处理速度

QPS 表示每秒请求数。假设导出高峰每分钟 60 个申请，单任务平均占用执行位置 20 秒：

```text
到达速度 = 60 / 60 = 1 个/秒
单个执行位置的处理速度 = 1 / 20 = 0.05 个/秒
```

| 执行位置数 | 理想处理能力 | 持续到达 60 个/分钟时的结果 |
| --- | --- | --- |
| 5 | 15 个/分钟 | 每分钟净积压 45 个 |
| 20 | 60 个/分钟 | 没有余量，任何波动都可能积压 |
| 25 | 75 个/分钟 | 理想情况下每分钟可消化 15 个历史积压 |

这是按平均耗时的理想估算，不是可交付的性能结论。多个任务可能争抢同一数据库连接或磁盘，需要测量后修正。

稳定条件下，平均完成速度乘平均执行时长，可以估算平均正在执行的任务数：这里约为 20。若要估算包含排队的平均未完成总量，需要使用“排队＋执行”的平均总时长；两者都不能直接保证最大并发或队列长度。

### 2. 积压恢复

假设已有 600 个积压，新增仍为 60 个/分钟，系统能稳定处理 75 个/分钟：

```text
恢复时间 = 600 / (75 - 60) = 40 分钟
```

加入队列能保存等待任务，不会自动增加处理速度。若处理速度不超过新增速度，单纯等待不能清空积压。

### 3. 存储量

另假设日常平均每分钟 2 个申请、每日活跃 8 小时、平均文件 2 MiB、保存 7 天：

```text
每日文件数 = 2 × 60 × 8 = 960
每日文件体积 = 960 × 2 MiB = 1.875 GiB
七天原始文件体积 = 13.125 GiB
```

索引、元数据、副本、备份、临时失败文件另计。高峰值用来估算处理余量，日常平均用来估算长期体积，不能混用。

## 五 先确定谁拥有状态，再划组件

页面的一个状态需要明确由谁修改，服务端也是如此。先给出最简单的职责分配：

| 责任 | 唯一负责者 |
| --- | --- |
| 校验申请、查询进度、检查下载权限 | 导出应用 |
| 保存请求、状态、版本和结果位置 | 任务数据库 |
| 生成文件 | 导出应用中的后台执行模块 |
| 保存实际文件 | 文件存储 |

应用内的模块可以先运行在同一进程。是否拆成独立服务，取决于容量、隔离、团队协作或独立发布需求。

为了能恢复，等待任务保存在数据库，后台执行模块按约定领取；仅放进内存线程池，进程重启可能丢失等待任务。

```mermaid
flowchart LR
    U["用户"] --> A["导出应用：提交和查询"]
    A --> D["任务数据库"]
    D --> W["后台模块：领取任务并执行"]
    W --> F["文件存储"]
    W --> D
```

这张图说明职责，不代表数据库主动调用代码。后台模块主动查询并领取待处理记录。

## 六 数据模型与接口围绕状态变化设计

下面是 MySQL 8 学习库中的表结构示例；它表达数据约束，不是一套完整运行服务：

```sql
CREATE TABLE export_task (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    request_id VARCHAR(64) NOT NULL,
    request_hash CHAR(64) NOT NULL,
    status VARCHAR(24) NOT NULL,
    version INT NOT NULL DEFAULT 0,
    object_key VARCHAR(256),
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    UNIQUE KEY uq_export_request (tenant_id, request_id)
);
```

| 字段 | 为哪个行为服务 |
| --- | --- |
| tenant_id + request_id | 同租户同一申请不重复创建 |
| request_hash | 相同申请编号带不同内容时能识别冲突 |
| status + version | 限制合法变化，拒绝旧执行者覆盖新结果 |
| object_key | 保存内部文件位置，下载时再检查权限 |

请求摘要应根据确定的参数规范生成；查询记录、比较摘要及返回已有任务的过程，要处理唯一约束下的并发冲突。具体实现见 [06](/06-事务与数据一致性/README/)与 [09](/09-分布式系统与服务协作/README/)。

接口按状态分开：

```text
POST /exports                 创建或复用同一申请
GET  /exports/501             查询已授权任务的状态
GET  /exports/501/download    再次校验权限与有效期后下载
POST /exports/501/cancel      发起取消请求
```

taskId 不是权限凭证，知道编号并不意味着可以下载。

## 七 失败方式决定恢复办法

先逐个分析失败，再把恢复方案放进综合设计：

| 故障点 | 可能已经发生什么 | 应有的处理 |
| --- | --- | --- |
| 任务写入成功，受理响应丢失 | 数据库已有任务 | 用同一申请编号查询或重试，返回已有任务 |
| 领取后进程停止 | 任务仍显示 RUNNING | 通过领取租约、心跳或对账识别；恢复要防旧执行者回写 |
| 文件写完，状态未更新 | 文件存在，数据库未成功 | 核对本次执行编号后恢复，或清理未引用文件 |
| 新执行已成功，旧执行才返回 | 两次计算都可能发生 | 版本条件更新只发布一个有效结果 |
| 文件存储不可用 | 计算可能完成但写入失败 | 明确失败或待恢复状态，保留原因并有限重试 |

租约只决定执行资格的时效，不会强制停止旧进程。保存结果仍需版本或执行编号校验；每次尝试可写入不同临时文件，只有成功提交的结果进入可下载状态。

发布也有失败边界。新增字段应先兼容旧代码，再上线依赖该字段的代码；重试、取消和状态查询在新旧版本同时运行时仍须兼容。恢复目标与演练见 [13](/13-部署运维与故障排查/README/)。

## 八 比较方案，并用实验推翻错误假设

给每个新增组件一个具体理由：

| 方案 | 解决什么 | 新增代价 | 何时再考虑 |
| --- | --- | --- | --- |
| 应用内后台模块 + 数据库任务表 | 初步持久化与恢复 | 轮询、领取与清理逻辑 | 基线方案先测量 |
| 独立执行服务 | 独立扩缩容、隔离慢任务 | 网络调用、部署和版本兼容 | 任务持续挤占接口资源 |
| 消息队列 | 更好地传递和缓冲异步任务 | 双写一致性、重复消费、积压治理 | 数据库轮询成本或异步协作确有问题 |
| 结果缓存 | 降低重复状态读取成本 | 陈旧结果、失效和权限隔离 | 查询负载确实成为瓶颈 |

实际验证先选最不确定的一点。例如“25 个执行位置能否稳定处理 75 个任务/分钟”，就用固定数据量、固定文件大小和相同下游环境测量吞吐、排队、错误和资源占用。若数据库先饱和，增加线程不能证明扩容有效。

## 九 综合案例 一份文件导出设计

把前面的概念组合成一份可评审的初版：

| 设计项 | 初版选择及依据 |
| --- | --- |
| 用户结果 | 先受理，随后查询并下载文件 |
| 业务规则 | 同一申请一个可见成功结果，下载校验租户与有效期 |
| 基线结构 | 一个应用、任务数据库、文件存储，后台模块与接口分配资源预算 |
| 容量 | 高峰 60 个/分钟，20 秒平均耗时；25 执行位置作为待测起点 |
| 数据 | 持久任务状态、唯一申请编号、请求摘要、执行版本、结果位置 |
| 恢复 | 幂等查询、领取超时识别、版本化发布结果、未引用文件清理 |
| 观测 | 受理时长、完成时长、队列最老年龄、成功率、数据库连接、执行饱和度 |
| 演进条件 | 量化接口受影响、积压超目标或数据库轮询成本，再选择隔离或队列 |

这是一份带假设的设计实例。运行性能、恢复和越权结论，都需要对应实验，不能由组件图代替。

后续可把同一方法用于指标版本发布或异步作业生成：先重写用户结果、状态和数据约束，再复用设计步骤，不直接复用这里的规模数字。

## 十 练习与验收

1. 把高峰改成每分钟 120 个申请，其他假设不变。计算 25 个执行位置是否会积压，再提出需要测量的瓶颈。
2. 把文件保存期改成 30 天，加入 2 份存储副本，重新估算容量并注明备份是否另算。
3. 写出“提交成功但响应丢失”“旧执行者晚返回”的时序，逐项核对不变量。
4. 为一个关键假设设计实验：固定输入、负载和环境，给出通过与推翻条件。

验收材料是需求表、状态图、数据模型、容量计算、失败表和实验结果。能解释为何选择当前方案，以及什么证据出现时需要修改方案。

通用 Java 学习按 Java 25；公司业务案例保留 Java 8 兼容要求。中文主读顺序与环境边界见 [学习版本与中文资料](/参考资料/学习版本与中文资料/)。
