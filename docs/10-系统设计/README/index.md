# 系统设计 Roadmap

| 类别 | 作用 | 前端类比 | 类比边界 |
| --- | --- | --- | --- |
| 需求与正确性 | 定义要交付的结果与不能违反的规则 | 需求澄清、交互状态 | 还要覆盖数据、重复请求和故障结果 |
| 目标与容量 | 判断服务表现与资源是否够用 | 性能目标与测量 | 排队、下游限制和恢复同样影响用户 |
| 结构与取舍 | 根据约束划职责、选方案 | 模块与状态归属 | 拆服务会增加网络与独立提交成本 |
| 验证与演进 | 用业务证据判断何时调整设计 | 灰度与用户反馈 | 包括长期流量、故障与数据恢复 |

## 本阶段学习定位

**按需深入。** 先积累服务需求和运行证据；遇到容量、边界、扩展或恢复约束时，再系统完成本路线。

## 目标与前置条件

目标是从需求推导一个能实现、能验证、能恢复的方案，而非先列技术组件。

[04 分层](/04-分层架构与业务建模/README/)与 [05 数据库](/05-数据库设计与SQL/README/)基础后可开始。事务、并发、缓存和服务协作部分按 [06](/06-事务与数据一致性/README/)—[09](/09-分布式系统与服务协作/README/)对应知识补齐。

## 学习方式与顺序

按“业务问题 → 正确性与运行约束 → 资料 → 方案中的体现”推导设计。先有当前可交付的基线，再用实际测量比较选择；概念学习与需求评审同步推进。

## 一 逐个知识点学习

### 1. 需求与业务不变量

**业务问题：** 用户最终需要得到什么，哪些结果即使重试或故障也不能发生？

**概念与保证：** 受理、完成、失败与未知是不同状态；重复、并发、权限和状态约束需要可观察的业务规则。

**项目中看什么：** 从需求表、接口和状态转换查到每条规则的负责者，明确不覆盖范围，不先罗列组件。

**教程与讲解：** [廖雪峰项目架构](https://liaoxuefeng.com/books/java/springcloud/architecture/index.html)；[需求](/10-系统设计/典型案例/#一-需求先写成可以观察的行为)、[不变量](/10-系统设计/典型案例/#二-业务不变量定义哪些结果不能发生)。

### 2. 可测量的服务目标

**业务问题：** 接口很快返回，是否说明用户的导出任务也很快完成？

**概念与保证：** SLI 是测量口径，SLO 是目标。分母、窗口、流量和失败定义不一致，数字就不能直接比较。

**项目中看什么：** 区分受理时长、完成时长、成功率、分位数与最老任务年龄，把目标连到用户结果。

**教程与讲解：** [Google SRE 服务目标](https://sre.google/sre-book/service-level-objectives/)；[测量口径](/10-系统设计/典型案例/#三-服务目标需要定义测量口径)。

### 3. 容量与瓶颈

**业务问题：** 现有资源能支撑多少工作，积压出现后多久才能消化？

**概念与保证：** 到达速度、处理速度、在途量、保存周期与资源配额分别约束方案。平均值只能用于带前提的估算。

**项目中看什么：** 容量计算注明单位、数据分布与假设，再查 CPU、连接、磁盘、网络和外部配额的真实限制，记录成本敏感项。

**教程与讲解：** [SRE 过载处理](https://sre.google/sre-book/handling-overload/)；[容量与假设](/10-系统设计/典型案例/#四-容量估算先写单位与假设)。

### 4. 职责、数据模型与接口

**业务问题：** 哪些状态应由谁维护，拆分后新增什么网络和提交代价？

**概念与保证：** 先确定数据所有权与状态转换，再选模块或服务边界；同步请求与异步任务各有结果、查询、取消和兼容约定。

**项目中看什么：** 从现有服务或模块化单体基线出发，查模型、唯一约束、版本条件和错误时序，给每个新增组件一个理由。

**教程与讲解：** [职责](/10-系统设计/典型案例/#五-先确定谁拥有状态再划组件)、[模型与接口](/10-系统设计/典型案例/#六-数据模型与接口围绕状态变化设计)；结合[04](/04-分层架构与业务建模/README/)、[05](/05-数据库设计与SQL/README/)。

### 5. 故障、恢复与运营

**业务问题：** 哪一步失败会留下什么，用户看见什么，谁能恢复？

**概念与保证：** 超时、重复、进程停止、存储故障和发布中断有不同状态后果；恢复能力还受权限、观测和资源预算约束。

**项目中看什么：** 检查故障表、关联标识、恢复入口、并发/队列/连接/重试预算，以及数据迁移和回退所需证据。

**教程与讲解：** [失败与恢复](/10-系统设计/典型案例/#七-失败方式决定恢复办法)、[AWS 评审框架](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)；结合[12](/12-安全与权限/README/)、[13](/13-部署运维与故障排查/README/)。

### 6. 比较与验证

**业务问题：** 哪种方案当前足够，什么事实出现时才值得演进？

**概念与保证：** 正确性、性能、交付时间、长期成本和运营负担需要一起比较；未知假设与已测保证分别标明。

**项目中看什么：** 优先测量最可能推翻选择的条件，对比相同数据、负载与下游环境，定义迁移和回退的触发条件。

**教程与讲解：** [方案与证据](/10-系统设计/典型案例/#八-比较方案并用证据检查关键假设)、[OpenTelemetry](https://opentelemetry.io/docs/concepts/observability-primer/)。

## 二 综合案例 文件导出设计

[文件导出设计](/10-系统设计/典型案例/#九-综合案例-一份文件导出设计)把用户结果、状态、规模、数据、故障和观测放进同一份方案。案例数字是计算假设，实际指标版本发布或作业生成需求必须重新核对流量、口径与约束。

## 三 业务验证

| 要核对什么 | 业务证据 |
| --- | --- |
| 结果与正确性 | 需求表、状态图、权限与重复请求规则，正常及失败时序 |
| 容量与成本 | 带单位和分布的估算、真实测量、配额与成本口径，注明尚未验证假设 |
| 故障与恢复 | 各提交点的状态、旧执行者晚返回、恢复责任及结果确认 |
| 取舍与演进 | 替代方案、关键约束、迁移代价和改变选择的条件 |

当前设计涉及性能、故障恢复或越权保证时，应保留对应测量和验证；组件图、平均值或一次压测都不能独立证明生产可用。
