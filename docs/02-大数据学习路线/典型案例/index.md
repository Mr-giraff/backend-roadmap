# 大数据组件与数据链路典型案例

## 技能迁移表

| 前端已有经验 | 数据能力 | 需要补上的差异 |
| --- | --- | --- |
| 展示订单数、金额与维度 | 定义口径与数据粒度 | 一行代表什么、状态和重复规则先约定 |
| 读取 schema | 理解表、字段、位置和分区 | 表描述存在还要核实文件和读取权限 |
| 对数组过滤、分组、求和 | 分布式批处理 | 数据交换、任务分配与失败恢复会影响执行 |
| 持续更新页面 | 流处理 | 事件时间、窗口、迟到和状态需要明确 |
| 排查页面数据不对 | 数据质量与链路定位 | 找到输入到输出中第一处偏离的位置 |

本篇串联四个已拆开的单元。先读[分布式计算基础](/02-大数据学习路线/01-分布式计算基础/典型案例/)、[Hive](/02-大数据学习路线/02-Hive/典型案例/)、[Spark](/02-大数据学习路线/03-Spark/典型案例/)、[Flink](/02-大数据学习路线/04-Flink/典型案例/)的概念说明，再沿当前业务的输入、转换、状态和输出组织代码阅读与验证。

## 一 一行代表什么，决定能怎样统计

| 输入粒度 | 样本 | COUNT(*) | COUNT(DISTINCT order_id) |
| --- | --- | --- | --- |
| 订单明细 | 101/A/6000、101/B/4000 | 2 | 1 |

统计订单数时，两个商品明细只对应一笔订单。本篇的另一组固定样本已约定为“订单最终状态”，金额单位为分，同一统计日，完全相同的重复行只算一次，取消订单不计入。

原始五行见 [orders.csv](/assets/02-大数据学习路线/examples/orders.csv)。真实业务存在状态版本时，需要按业务键和版本选有效记录；本例的 DISTINCT 只处理完全重复行。

## 二 存储保存数据，元数据说明怎样读取

沿 [Hive 表与文件说明](/02-大数据学习路线/02-Hive/典型案例/#二-表描述怎样读取文件)分别检查：表定义、存储位置、实际文件、分区登记和访问权限。

```text
表描述：order_id、region、amount_cents、status、分区 dt
文件：同一统计日的五条订单记录
分区：dt=2026-10-26 → 对应文件目录
```

外部表 DDL 不负责自动生成文件。应用模型记录、Hive 表描述和实际数据是不同对象。

## 三 批处理先明确输入与口径

[Spark 单元](/02-大数据学习路线/03-Spark/典型案例/#一-固定输入先把计算口径写清楚)与 [batch.sql](/assets/02-大数据学习路线/examples/batch.sql)用同一输入说明过滤、去重和地区聚合，按本例口径结果为：

| region | order_count | amount_cents |
| --- | --- | --- |
| east | 2 | 15000 |
| south | 1 | 8000 |

该口径对应三笔有效订单、合计 23000 分，业务改动需将源明细、计算规则和实际输出对账。临时视图只存在于当前会话，后续保存到持久表或发布分析服务需要另外完成。

## 四 分布式执行把同一计算拆给多个进程

在[共同基础](/02-大数据学习路线/01-分布式计算基础/典型案例/#三-shuffle-让相同分组的数据汇合)解释数据为什么需要交换，再在 [Spark 计划与任务](/02-大数据学习路线/03-Spark/典型案例/#三-计划说明怎样算运行界面说明算得怎样)找到实际证据。

观察输入分区、聚合前后的数据量、交换位置、任务耗时和失败记录。少数任务慢可能与倾斜、资源、磁盘或外部依赖有关，需要指标区分。

## 五 流处理需要规定时间与窗口

[Flink 窗口说明](/02-大数据学习路线/04-Flink/典型案例/#三-用三个固定事件验证窗口边界)与 [window.sql](/assets/02-大数据学习路线/examples/window.sql)用以下事件解释时间归属：

| 窗口 | 样本事件时间 | 预期点击数 |
| --- | --- | --- |
| [10:00,10:01) | 10:00:10、10:00:20 | 2 |
| [10:01,10:02) | 10:01:01 | 1 |

这组预期仅说明有限输入的窗口边界。持续流中的乱序、迟到、Watermark 推进和恢复，需要当前作业的时间进度、状态和输出证据支持。

## 六 状态恢复与外部写入要一起检查

沿 [Flink 恢复时间线](/02-大数据学习路线/04-Flink/典型案例/#四-状态保存到哪里失败后从哪里继续)核对输入位置、内部状态和输出结果。

```text
读取事件 → 更新内部状态 → 写入外部系统 → 进程停止
```

恢复时能否重读、外部结果是否重复，取决于输入、检查点与输出的配合。框架内部的状态一致性不能单独证明外部操作只执行一次。

## 七 调度和分析引擎解决不同问题

| 层次 | 本例职责 | 先查的证据 |
| --- | --- | --- |
| 平台任务调度 | 等待上游、提交订单汇总、安排补数 | 依赖、参数、运行实例 |
| 集群资源管理 | 分配 CPU、内存与执行资源 | 队列和资源等待 |
| 引擎内部调度 | 把计算交给任务执行 | 计划、任务、数据交换、背压 |
| 分析服务 | 查询已导入的汇总 | 导入状态、数据版本与权限 |

StarRocks、ClickHouse 等分析引擎留作业务扩展。同一输入分别核对 DDL、导入、更新和查询行为；兼容 MySQL 协议不能单独证明 SQL 与事务语义相同。可按需阅读 [StarRocks 中文架构](https://docs.starrocks.io/zh/docs/introduction/Architecture/)。

## 八 质量与血缘让结果可以解释

| 检查 | 样本预期 | 发现偏差时先检查 |
| --- | --- | --- |
| 原始行数 | 5 | 文件位置和读取范围 |
| 取消订单数 | 1 | 状态口径与解析 |
| 有效且去重的订单数 | 3 | 过滤和去重规则 |
| 汇总总额 | 23000 分 | 金额单位、重复和关联条件 |

```text
五条原始记录 → 过滤 PAID → 完全重复行去重 → 按地区汇总
```

这条转换关系是最小血缘。再记录输入批次、统计日、脚本版本和运行编号。页面结果旧时，逐步核对源数据、清洗、运行实例、输出分区、导入和查询缓存，找到第一处变旧的位置。

## 九 综合案例 从口径走到可核对的结果

| 单元 | 项目中要理解什么 | 对应证据 |
| --- | --- | --- |
| 分布式计算基础 | 分区与数据交换图 | 手算过程、任务与资源职责 |
| Hive | 外部表与分区查询 | 表定义、文件位置、SHOW PARTITIONS、查询结果 |
| Spark | 批处理执行 | SQL、预期与实际结果、执行计划、任务界面 |
| Flink | 时间窗口与恢复 | 事件序列、窗口结果，另附持续流状态和重启记录 |
| 链路串联 | 质量与故障定位 | 行数金额对账、首个偏离位置、恢复后结果 |

Spark 接 Hive、Flink 接 Kafka 和外部 Sink 时，需要核对实际兼容配置、身份与权限。单个环节结果正确，不证明全链路时效、恢复和输出一致性已经成立。

## 十 业务验证

| 当前变化 | 必须检查的业务结果 |
| --- | --- |
| 口径、去重或状态版本 | 一行代表什么，有效版本怎样选择，源明细和聚合能否对账；DISTINCT 不自动解决多版本问题 |
| 表、分区或来源变更 | 元数据、文件、身份、读取范围与实际输入一致 |
| 时间窗口或迟到规则 | 事件时间、Watermark、窗口边界和实际输出符合产品约定 |
| 重跑、故障恢复或输出切换 | 输入位置、内部状态与外部结果共同核实，识别少算、重复与旧值 |
| 性能与时效 | 执行计划、数据规模、资源等待、背压和业务结果的可见时间支持结论 |

验证内容按当前需求及改动范围选择，记录数据、SQL、引擎与连接器版本和运行标识。固定样本的预期不作为真实引擎执行、资源调度或恢复保证的通过记录。
