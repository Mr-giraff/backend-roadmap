# 部署运维与故障排查 Roadmap

| 类别 | 作用 | 前端类比 | 类比边界 |
| --- | --- | --- | --- |
| 环境与制品 | 明确实际运行的代码、配置和资源 | 构建与发布前端文件 | Java 服务维护长期进程、线程和连接 |
| 健康与发布 | 判断是否接流量、是否继续发布 | 页面与关键接口验证 | 进程存活不等于业务可用，数据也不随代码自动回退 |
| 可观测与诊断 | 用证据定位时间与失败来源 | Console、Network、性能分析 | 需要跨实例、线程和服务关联 |
| 恢复 | 恢复服务和业务数据 | 版本回退与数据导出 | 备份必须恢复验证，外部副作用需对账或补偿 |

## 本阶段学习定位

**贯穿需求实战。** 先会启动、看日志、打断点、核对配置和实际运行版本；集群运维、备份恢复和完整发布体系按职责深入。

## 目标与前置条件

能够交付一个可追溯、可验证、可恢复的 Java 服务，并用证据定位常见故障。

先完成 [02 工程](/02-工程构建与研发流程/README/)、[03 接口](/03-HTTP与Spring服务开发/README/)基础；数据库、线程与跨服务诊断分别结合 [05](/05-数据库设计与SQL/README/)、[07](/07-并发与异步编程/README/)、[09](/09-分布式系统与服务协作/README/)。运行 JDK 与诊断工具核实实际版本，不只看源码编译目标。

## 学习方式与顺序

从当前发布或故障出发，先明确用户影响，再理解制品、进程、资源与恢复的保证，读对应工具资料，最后核对实际运行证据。[典型案例](/13-部署运维与故障排查/典型案例/)围绕版本不一致、未就绪、慢请求和数据恢复解释判断过程。

## 一 逐个知识点学习

### 1. 进程、端口与环境

**业务问题：** 访问失败时，程序没运行、地址不可达和业务拒绝分别在哪一层？

进程存在、端口监听和业务可用是不同事实。账号、权限、工作目录、环境变量与资源限制影响进程行为；DNS、连接、TLS 和 HTTP 错误需要按边界区分。

**代码与资料：** 读[进程与端口](/13-部署运维与故障排查/典型案例/#一-进程与端口说明不同事实)，从实际 PID、监听地址和请求结果交叉判断；[JDK 排查指南](https://docs.oracle.com/en/java/javase/21/troubleshoot/)按运行 JDK 核对。

### 2. 制品与配置

**业务问题：** 源码已修改，为什么线上行为仍旧，另一实例却不同？

源码版本、构建产物、运行配置和进程需要一一对应。构建时与运行时配置不同，密钥不应进入制品或日志；线程、连接、队列和存储都有容量及退出边界。

**代码与资料：** 读[制品与进程](/13-部署运维与故障排查/典型案例/#二-制品配置与进程需要分别确认)，沿提交、构建标识、启动参数、配置来源追到当前实例；容器职责查 [Docker 镜像说明](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/)。

### 3. 健康、发布与回退

**业务问题：** 新实例启动后是否可以接流量，失败发布该回退什么？

存活、启动完成、就绪与关键业务结果各自承担不同判断。发布需要观察窗口、停止条件与恢复验证；代码回退不自动撤销数据、结构变化和远程操作。

**代码与资料：** 读[健康状态](/13-部署运维与故障排查/典型案例/#三-存活就绪与业务结果分开验证)和[发布回退](/13-部署运维与故障排查/典型案例/#四-发布先定义观察条件再定义回滚)，核对实际探测与放行策略；所用平台采用 Kubernetes 时读[探针职责](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)。

### 4. 可观测性

**业务问题：** 同一个慢请求在网关、服务、数据库与队列中分别花了多久？

日志记录事件，指标反映分布和趋势，追踪组织调用关系。关联标识、版本、实例和时间窗口帮助拼接证据；采样或上下文缺失不能直接证明调用未发生。

**代码与资料：** 读[日志、指标与追踪](/13-部署运维与故障排查/典型案例/#五-日志指标与追踪互相补充)，跟踪当前请求与异步完成过程；基础查[日志教程](https://liaoxuefeng.com/books/java/exception/jdk-logging/index.html)，机制查 [OpenTelemetry](https://opentelemetry.io/docs/concepts/observability-primer/)。

### 5. 诊断与止损

**业务问题：** 请求慢是在计算、排队、等锁、等连接还是等下游？

相同现象可能有不同原因，需要能区分假设的证据。线程快照、CPU、池指标和调用耗时应互相印证；重启可能止损，却不能单独证明根因，诊断动作也有停顿和数据风险。

**代码与资料：** 读[慢请求定位](/13-部署运维与故障排查/典型案例/#六-慢请求先分辨等待在哪里)，按实际运行版本选择 [JDK 工具](https://dev.java/learn/jvm/core-tools/)和[监控排查资料](https://dev.java/learn/jvm/monitoring-troubleshooting/)。

### 6. 备份与恢复

**业务问题：** 备份文件存在，能否在目标时间内恢复到业务可用状态？

RTO 约束恢复时间，RPO 约束允许丢失的数据范围。数据库、对象文件、配置和消息状态需要相容的恢复点；恢复结果要核对结构、约束、关键值及应用读取。

**代码与资料：** 读[备份与恢复](/13-部署运维与故障排查/典型案例/#七-备份要通过恢复验证)，按当前数据保护职责检查恢复方案；数据库工具查 [mysqldump](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html)，目标定义查 [SRE 服务目标](https://sre.google/sre-book/service-level-objectives/)。

## 二 综合案例

[失败发布到故障恢复](/13-部署运维与故障排查/典型案例/#八-综合案例-从失败发布到故障恢复)将版本、探测、请求和数据状态连成一条调查链。处理实际问题时先定位影响与最近变更，提出可区分的原因，再选择副作用明确的止损和恢复动作。

## 三 业务验证

按当前职责与发布范围收集证据：

| 业务情况 | 必要验证 |
| --- | --- |
| 发布或回退 | 版本、配置、就绪、关键请求、错误与延迟符合事先定义的放行条件 |
| 客户端超时 | 关联远端日志、线程或任务状态，说明操作是否仍在执行及副作用在哪里 |
| 性能改动 | 同口径的负载、输入规模、延迟分布、错误与资源数据支持结论 |
| 备份或恢复方案变更 | 在隔离恢复目标中核对结构、数据、应用读取、恢复耗时及缺失范围 |

实际恢复演练是恢复能力的业务证据，按数据保护职责安排。验证计划以当前发布、性能或数据保护需求的影响范围为依据。
