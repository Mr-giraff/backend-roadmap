# 部署运维与故障排查典型案例

## 技能迁移表

| 前端已经会的事 | 后端对应能力 | 需要补上的差异 |
| --- | --- | --- |
| 构建 dist 并确认版本 | 构建 JAR、确认进程与制品 | 进程可能仍加载旧代码或另一套配置 |
| Console、Network、性能面板 | 日志、指标、链路与线程证据 | 需要跨请求、实例和服务定位，不能任意暂停 |
| 回退前端文件 | 回滚代码与配置 | 数据库和远端副作用不一定随代码回退 |
| 通过 URL 看页面是否可用 | 健康与业务验证 | 端口、进程存活和业务正确是不同层次 |
| 导出数据 | 备份与恢复演练 | 能生成文件，还要证明可以恢复并继续使用 |

从一次发布后的异常出发，区分版本、配置、运行进程、依赖与数据状态。短例帮助说明证据能够支持什么结论；实际诊断和恢复按当前服务的职责、环境和权限执行。

## 一 进程与端口说明不同事实

进程是正在运行的程序，端口是它可能监听的入口。程序未启动、只监听本机、网关路由错误和业务拒绝，会产生不同现象。

| 观察 | 能证明什么 | 还不能证明什么 |
| --- | --- | --- |
| 找到 Java PID | 有一个 Java 进程 | 就是目标服务，加载了正确制品，业务正常 |
| 目标端口监听 | 某个进程可以接收连接 | 数据库、配置和权限检查都正确 |
| 关键接口返回目标版本和结果 | 当前请求经过了对应逻辑 | 其他实例及其他业务路径同样正常 |

从运行归属明确的进程开始核对命令行、监听地址、账号、工作目录与配置来源。DNS、连接、TLS、HTTP 和业务响应是不同边界，不能把所有失败都归为网络异常。

## 二 制品、配置与进程需要分别确认

源码提交、构建产物、运行配置和实例需要关联。源码已改、镜像已生成或发布平台显示成功，都不能单独证明当前流量使用新代码。

```text
源码提交 → 构建标识与依赖 → JAR/镜像 → 启动参数与配置 → 实例 → 业务响应
```

[OpsDemo.java](/assets/01-Java学习路线/09-部署与运行维护/examples/OpsDemo.java)的短实现区分版本、就绪与业务处理，用来阅读进程如何暴露信息；它没有真实数据库、完整指标或发布平台，不能用它推断线上发布能力。

实际服务应能关联源码版本、制品标识、运行 JDK、配置来源与实例。镜像保存打包内容，容器是运行实例，持久卷与外部数据库有独立生命周期。优雅退出还要确认停止接流量、在途请求、异步任务和连接怎样收尾。

## 三 存活、就绪与业务结果分开验证

| 信号 | 回答的问题 | 业务上的用法 |
| --- | --- | --- |
| 存活 | 进程是否还能按探测契约工作 | 支持进程恢复判断，不证明全部依赖可用 |
| 启动完成 | 初始化是否已走到可以进行后续判断的位置 | 防止把正常长启动误当故障 |
| 就绪 | 当前实例是否应该接收业务流量 | 根据必要依赖与自身状态决定是否放行 |
| 关键业务请求 | 当前身份、输入和依赖能否得到正确结果 | 核对真实用户路径及数据状态 |

探针职责按[运行平台](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)和服务契约设置。一个固定成功响应不足以证明服务已就绪；未就绪实例也不应仅因进程存活而被接入流量。

## 四 发布先定义观察条件，再定义回滚

| 检查对象 | 放行依据 | 异常时需要判断什么 |
| --- | --- | --- |
| 版本与配置 | 目标实例使用预期制品和配置 | 是否部署到正确环境，是否仍有旧实例或旧值 |
| 就绪与流量 | 必要依赖满足接流量条件 | 停止推进、移除流量或恢复原版本 |
| 业务结果 | 关键请求及数据状态符合规则 | 哪些操作已发生，回退能否兼容 |
| 错误、延迟与资源 | 在约定负载及观察窗口内符合目标 | 是暂时波动、容量瓶颈还是功能回归 |

代码或配置回退不会自动撤销数据库写入和已完成的远程调用。结构变更、新旧实例共存、消息格式和错误数据需要分别制定兼容、修复或补偿方案。恢复后仍需核对业务结果。

## 五 日志、指标与追踪互相补充

日志记录事件，指标反映一段时间的分布，追踪组织同一请求的多个步骤。

| 证据 | 常见信息 | 可以支持的判断 |
| --- | --- | --- |
| 日志 | 时间、实例、版本、请求或操作标识、错误分类 | 某次操作经过哪里、在哪个步骤失败 |
| 指标 | 请求数、错误率、延迟分布、池占用、队列年龄 | 影响是否持续、规模多大、资源是否饱和 |
| Trace | 入口、数据库、远端调用各段耗时 | 等待发生在哪一段，哪个依赖异常 |

关联标识用于诊断，不提供身份权限。敏感字段不得原样记录；采样、上下文丢失和异步边界也可能造成追踪缺段。告警应能关联用户影响、持续时间、负责人和诊断入口，而不只描述一个瞬时指标。

## 六 慢请求先分辨等待在哪里

客户端超时只说明调用方没有按时获得结果。服务端可能仍在计算、等锁、排队或调用下游，副作用也可能已经完成。

| 相似现象 | 更有区分力的证据 | 不能直接得出的结论 |
| --- | --- | --- |
| CPU 很高且请求慢 | 多次线程采样、热点方法、CPU 时间 | 一定是数据库慢 |
| CPU 低但数据库调用长 | 慢 SQL、锁等待、连接池与调用耗时 | 增加应用线程就能变快 |
| 下游调用耗时长 | Trace、连接与读取时限、下游日志 | 调用方超时代表远端没执行 |
| 大量任务排队 | 活跃线程、队列年龄、连接与拒绝数 | 无限加大队列可以解决过载 |

诊断工具匹配实际运行 JDK，先确认 PID 和环境。一次线程快照可能错过短暂等待，需要结合时间线和多次采样。内存问题还要分清堆、线程栈、元空间、本地内存和 GC；大转储可能产生停顿、占用磁盘并包含业务数据。

## 七 备份要通过恢复验证

RTO 表示允许多长时间恢复，RPO 表示允许损失多长时间范围内的数据。备份文件存在，只能证明产生了文件，不能证明它可恢复或满足业务目标。

```text
备份与日志范围 → 隔离恢复目标 → 结构和数据校验 → 应用读取 → 对账与恢复耗时
```

恢复验证需要核对表结构、约束、记录数量、关键值、对象文件及应用读取。源库在备份点后的变化，决定恢复后需要怎样补数或对账；跨数据库、对象存储和消息状态还需相容的恢复点。工具参数、版本限制与一致性边界按 [MySQL 备份资料](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html)及项目方案核对。

## 八 综合案例 从失败发布到故障恢复

假设发布后部分请求返回旧配置，另一些请求超时。先核对受影响实例和业务操作，再沿下面的链路组织判断：

| 调查阶段 | 需要的证据 | 支持的决策 |
| --- | --- | --- |
| 确认版本和配置 | 实例、制品、启动参数、配置实际读取值 | 是发布不一致，还是业务代码没有使用新值 |
| 检查接流量条件 | 就绪、关键依赖、错误与延迟 | 是否停止推进或移除问题实例 |
| 确认在途工作 | 请求关联日志、线程、下游与操作状态 | 哪些可以重试，哪些应先查询结果 |
| 恢复并验证 | 恢复后的版本、关键请求与数据对账 | 用户路径和业务状态是否恢复 |
| 复盘原因 | 变更、机制、资源与恢复时间线 | 哪些原因已证实，哪些仍需核实 |

重启或回退可以止损，但不能单独证明根因。涉及数据恢复时，恢复时间、缺失范围及外部副作用需要独立说明。

## 九 业务验证

当前需求按实际影响范围保留版本、配置、关键请求、正常与拒绝结果、资源和恢复证据。发布验证使用明确观察窗口与停止条件；性能改动使用可比较的输入与负载；备份方案需要真实隔离恢复结果支持。

参考 OpsDemo 只有编译记录，未据此确认监听请求、JVM 采样或数据库恢复已经通过。实际能力的验证范围见[统一记录](/参考资料/示例验证说明/)。学习环境和存量业务兼容要求按[版本说明](/参考资料/学习版本与中文资料/)核对。
