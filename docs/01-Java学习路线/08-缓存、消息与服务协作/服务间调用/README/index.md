# 分布式系统与服务协作 Roadmap

| 类别 | 作用 | 前端类比 | 类比边界 |
| --- | --- | --- | --- |
| 服务通信 | 跨进程交换信息 | 请求多个接口 | 远端独立提交，超时可能留下未知结果 |
| 幂等与一致性 | 在重试和部分成功下保持业务规则 | 防重复与状态管理 | 约束需要持久化并承受多实例竞争 |
| 恢复与治理 | 控制资源、发现卡住工作并收尾 | 重试、状态刷新与错误提示 | 需要服务侧查询、补偿、对账和受控恢复 |
| 复制与共识 | 在多个副本间定义可见与提交规则 | 多端同步仅有局部相似 | 网络分区、时钟和节点故障需要明确模型 |

## 本阶段学习定位

**按需深入。** 服务发现、配置和 RPC 上手先走 08；本路线用于幂等、部分成功、消息一致性和恢复等可靠性问题。

## 目标与前置条件

能够为每个失败点说明“是否执行、是否提交、怎样确认、谁来恢复”，并验证重复请求不会增加错误业务结果。

深入持久化与恢复时需要 [接口](/01-Java学习路线/05-Web与Spring服务开发/README/)、[本地事务](/01-Java学习路线/04-数据库与持久化/数据变更与事务/README/)；消息部分先完成 [Kafka 消费位置与重复处理](/01-Java学习路线/08-缓存、消息与服务协作/README/)。结合 [并发与JVM](/01-Java学习路线/07-并发与JVM/README/)理解线程、截止时间和资源边界。

服务框架上手见 [微服务开发与注册配置](/01-Java学习路线/08-缓存、消息与服务协作/微服务调用与注册配置/README/)。

## 学习方式与顺序

从一个有写入或跨服务副作用的请求进入，先确定进程与提交边界，再理解未知结果、幂等与恢复。资料按当前问题选读，不把全套一致性机制作为普通调用的前置。

## 一 逐个知识点学习

### 1. 真实进程边界

**业务问题：** 看似普通的方法调用，实际是否经过网络或另一个独立提交方？

**概念与保证：** 仓库、模块、JAR、进程、实例与机器不是同一个边界。SDK 能封装调用形式，不能消除远端失败。

**项目中看什么：** 沿客户端实现和生效配置确认目标地址、协议与运行进程，标明谁拥有数据和提交事务。

**教程与讲解：** [廖雪峰项目架构](https://liaoxuefeng.com/books/java/springcloud/architecture/index.html)；[包与进程](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#一-先区分代码包与运行进程)。

### 2. 未知结果与调用预算

**业务问题：** 调用超时后，远端是否已经执行，继续重试会增加多少工作？

**概念与保证：** 客户端没收到结果，不等于远端没有提交。整体截止时间覆盖排队、连接、执行与退避，多层重试可能放大流量。

**项目中看什么：** 查看查询结果的操作编号、重试责任层、剩余预算及连接/并发/队列限制；区分业务拒绝、短暂不可达和过载。

**教程与讲解：** [AWS 超时、重试与退避](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)；[未知结果](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#二-超时后执行结果可能未知)、[调用预算](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#三-为整条调用分配时间与重试次数)。

### 3. 持久化幂等与状态转换

**业务问题：** 重复请求、并发请求和迟到结果，会不会产生两份记录或覆盖正确状态？

**概念与保证：** 稳定操作编号、租户范围、内容比较与唯一约束共同识别同一次操作。条件更新或版本号限制状态转换，PROCESSING 还需恢复责任。

**项目中看什么：** 核对首次写入与重复返回路径、唯一约束冲突处理、状态条件及查询入口；不要只依赖页面防抖或先查再写。

**教程与讲解：** [操作记录](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#四-用持久化记录识别同一次业务操作)、[状态机](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#五-状态机规定下一步允许做什么)；结合[事务](/01-Java学习路线/04-数据库与持久化/数据变更与事务/README/)。

### 4. 本地事件与消费去重

**业务问题：** 数据库提交后消息没发出，或业务已消费但确认丢失，怎样恢复？

**概念与保证：** 业务与 Outbox 在同一本地事务提交，发布仍可能重复；消费去重与业务修改在消费方自己的本地事务完成。跨服务不存在自动共享的本地事务。

**项目中看什么：** 定位每个数据库和消息确认点，检查稳定事件标识、发布状态、消费去重、位置推进及发布器并发认领。

**教程与讲解：** [Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)；[本地事件](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#六-outbox-把业务修改与待发送事件一起提交)、[消费去重](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#七-消费方也在本地事务中去重)。

### 5. 补偿、对账与恢复责任

**业务问题：** 工作停在中间时，谁能确认事实，哪些影响可以撤销，谁负责收尾？

**概念与保证：** 补偿是新的业务操作，不是抹除历史；对账发现应继续却未继续的状态。重复恢复本身也要安全。

**项目中看什么：** 检查操作/事件编号、长期中间态、恢复权限、审计、次数与告警，明确自动与人工处理边界；时间戳不独立证明严格因果。

**教程与讲解：** [补偿与对账](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#八-补偿与对账使流程能够收尾)；结合[运行排查](/01-Java学习路线/09-部署与运行维护/README/)。

### 6. 地址治理与复制入门

**业务问题：** 找到健康实例以后，为什么仍可能读到旧数据或无法继续提交？

**概念与保证：** 服务发现解决地址，复制解决副本；它们不自动保证业务幂等。复制延迟、网络分区和多数派决定各自的可见与提交边界。

**项目中看什么：** 先区分网关、实例选择、配置和数据读写路径，再按业务需要判断旧读、故障切换与一致性代价。

**教程与讲解：** [治理与副本](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#九-地址治理与复制各自解决什么问题)、[CAP 论文](https://www.comp.nus.edu.sg/~gilbert/pubs/BrewersConjecture-SigAct.pdf)、[Raft 论文](https://raft.github.io/raft.pdf)；框架入口在[微服务调用与注册配置](/01-Java学习路线/08-缓存、消息与服务协作/微服务调用与注册配置/README/)。

## 二 综合案例

[订单确认与履约](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/#十-综合案例-订单确认与履约)展示两个服务和消息系统的独立提交点。阅读时沿 req-7、evt-201 追踪订单、待发送事件、去重记录与履约结果，说明各处部分成功怎样被查询和恢复。

## 三 业务验证

| 要核对什么 | 业务证据 |
| --- | --- |
| 重复与未知结果 | 同 key 重试仍只有一份业务结果，不同内容可识别冲突，已有结果可查询 |
| 发布与消费恢复 | 数据库、消息及确认各边界的实际状态，恢复后结果完整且不重复产生副作用 |
| 过载与重试 | 截止时间、最多调用次数、队列与连接上限，不能把未知结果直接当失败重建 |
| 恢复责任 | 中间状态的确认渠道、负责人、受控入口、审计和最终状态 |

状态推演帮助理解，业务正确性仍由实际实现、持久化约束与运行记录证明。当前需求涉及哪个边界，就检查哪个边界。

## 四 按前置条件深入

| 方向 | 前置 | 深入能力 |
| --- | --- | --- |
| 调用治理 | 本页预算、[并发与JVM](/01-Java学习路线/07-并发与JVM/README/)、[部署与运行维护](/01-Java学习路线/09-部署与运行维护/README/) | 限流、隔离、熔断、连接池及剩余截止时间传播 |
| 事件契约 | [业务分层与建模](/01-Java学习路线/05-Web与Spring服务开发/业务分层与建模/README/)、[缓存、消息与服务协作](/01-Java学习路线/08-缓存、消息与服务协作/README/) | 版本、顺序、对象键、兼容发布和旧消息重放 |
| Outbox 并行发布 | 本页单发布器、[数据变更与事务](/01-Java学习路线/04-数据库与持久化/数据变更与事务/README/) | 认领、租约、锁、恢复、去重、清理与容量 |
| 分布式事务机制 | 当前需求涉及可恢复流程 | 比较 2PC、TCC、Saga 的参与方、阻塞和补偿成本 |
| 复制与一致性 | 读写历史与故障模型 | 读到自己写入、因果、线性与最终一致；故障切换和恢复边界 |
| 共识与锁 | 原始论文与组件保证 | 选主、日志复制、多数派；租约失效、旧执行者和外部递增令牌校验 |

先比较唯一约束、条件更新、幂等状态机，再决定是否需要分布式锁；不要求手写共识协议或自建注册中心。
