## 定位与前置条件

微服务调用与注册配置是服务开发的重点。Redis 和 Kafka 按**使用层**学习：先会接入 Redis、Kafka，解释它们的作用、部署角色和常见失败，再随真实需求深入。学到能验证缓存命中、发布消费、重复处理和积压即可进入项目；复杂缓存设计与跨系统一致性按需查阅。

前置为 [接口](/01-Java学习路线/05-Web与Spring服务开发/README/)与 [数据库](/01-Java学习路线/04-数据库与持久化/MySQL基础与部署/README/)的基本查询。通知写入用到 [本地事务](/01-Java学习路线/04-数据库与持久化/数据变更与事务/README/)；多线程消费者留到 [并发与JVM](/01-Java学习路线/07-并发与JVM/README/)。

消息主线使用 **Kafka**。Redis 基础仍以廖雪峰中文教程为主；Kafka 的分区、消费组和消费位置按官方资料核对。Java 学习环境遵循统一基线；本地 Kafka 示例选 4.2，JDK 支持范围按官方文档与统一学习基线核对。公司 Java 8 工程沿用兼容的客户端与框架版本，不能直接引入本学习环境的 Kafka 客户端。

## 学习方式与顺序

从一次查询或一条业务事件进入，按“业务问题 → 组件保证 → 官方资料 → 项目代码与配置”阅读。Redis、Kafka 先达到能接入和解释失败的使用层；复杂一致性在实际需求出现时进入[服务间调用](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/README/)。

## 三 业务验证

| 要核对什么 | 业务证据 |
| --- | --- |
| 缓存范围与时效 | 同编号不同租户不会串数据，展示陈旧与失效恢复符合约定 |
| 故障回源 | Redis 不可用时数据库压力与用户降级结果有明确上限 |
| 消费结果与恢复 | 事件标识、分区位置、数据库结果及重复事件的处理记录 |
| 处理能力 | 各分区积压、处理速率、失败与恢复用时，不能只看消费进程存活 |

验证围绕当前业务的风险展开；组件 CLI 能连通只证明连接和选定操作，不证明完整业务链路。

## 四 按需深入

| 深入主题 | 触发场景 | 查阅方向 |
| --- | --- | --- |
| Redis 性能与高可用 | 热键、大键、连接或切换问题 | 慢命令、内存淘汰、复制和故障恢复 |
| 缓存一致性 | 展示陈旧超标或失效失败 | [事务](/01-Java学习路线/04-数据库与持久化/数据变更与事务/README/)、[一致性](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/README/) |
| Kafka Java / Spring 接入 | 项目需要消费者或发送方改动 | 客户端兼容、序列化、手动提交、重平衡与处理时限 |
| 消息双写与恢复 | 数据库成功但事件未发布 | [Outbox 与恢复](/01-Java学习路线/08-缓存、消息与服务协作/服务间调用/典型案例/) |
| 复杂消息处理 | 需延迟重试、隔离和受控重放 | 明确 topic、位置、去重和恢复责任，再选择框架实现 |

RabbitMQ 仅在实际项目需要时选读，其队列与确认机制另按产品文档学习。
