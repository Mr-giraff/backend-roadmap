# 测试与质量保障典型案例

## 技能迁移表

| 前端已有经验 | 后端对应能力 | 需要补上的差异 |
| --- | --- | --- |
| 对纯函数写输入输出断言 | Java 单元测试 | 先明确行为，再选择测试框架 |
| 用假的请求实现控制返回值 | 测试替身与 Mock | 被替换边界之外的真实行为没有被证明 |
| 测组件与接口联动 | MVC、数据库和服务集成测试 | SQL、事务提交、协议转换需真实或足够接近的边界 |
| 回归旧页面调用 | 接口契约与兼容测试 | 类型、空值、错误码和大整数同样属于契约 |
| 根据异常复现问题 | 故障与并发测试 | 需要可控制的故障点及最终状态证据 |

先用一个确定的业务规则学习断言，再逐层引入框架和依赖。后面的“名称可用性”综合案例不预设真实数据库存在。

## 一 先定义行为，再写断言

断言用于比较预期结果与实际结果，不只是把结果打印出来。先规定一个规则：名称去除首尾空白后不能为空。

前端可以先这样描述：

```javascript
function normalize(raw) {
  if (raw == null || raw.trim() === '') throw new Error('名称不能为空');
  return raw.trim();
}
console.assert(normalize(' ODS ') === 'ODS');
```

Java 中的完整被测类 `NameRules.java`：

```java
public final class NameRules {
    private NameRules() {}
    public static String normalize(String raw) {
        if (raw == null || raw.trim().isEmpty()) {
            throw new IllegalArgumentException("名称不能为空");
        }
        return raw.trim();
    }
}
```

一个不依赖框架的检查入口 `RuleCheck.java`：

```java
public class RuleCheck {
    public static void main(String[] args) {
        String actual = NameRules.normalize(" ODS ");
        if (!"ODS".equals(actual)) {
            throw new AssertionError("expected ODS, got " + actual);
        }
        System.out.println("RuleCheck: PASS");
    }
}
```

预期输出 `RuleCheck: PASS`；若误删 trim，检查会失败。它证明了给定输入的结果，不证明 HTTP 参数绑定或数据库保存。

## 二 JUnit 把检查组织成可重复执行的测试

JUnit 提供断言、测试发现和报告。纯 JUnit 学习工程固定 Java 25、JUnit 6.1.3 与 Surefire 3.5.5；后面的 MVC 工程单独使用 Boot 依赖管理。Java 8 业务项目仍使用兼容它的原有测试版本。

下面测试所需的完整类是上一节的 NameRules，测试文件为 `NameRulesTest.java`：

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class NameRulesTest {
    @Test
    void trimsName() {
        assertEquals("ODS", NameRules.normalize(" ODS "));
    }

    @Test
    void rejectsBlank() {
        IllegalArgumentException error = assertThrows(
                IllegalArgumentException.class,
                () -> NameRules.normalize("   "));
        assertEquals("名称不能为空", error.getMessage());
    }
}
```

两个测试分别验证正常结果与明确拒绝。`assertThrows` 接收一段待执行代码，检查它是否抛出指定异常；不会把任意失败都当成正确。

在独立学习工程中，完整 POM 可写为：

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>study</groupId><artifactId>quality-demo</artifactId><version>1.0-SNAPSHOT</version>
  <properties>
    <maven.compiler.release>25</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>
  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId><artifactId>junit-jupiter</artifactId>
      <version>6.1.3</version><scope>test</scope>
    </dependency>
  </dependencies>
  <build><plugins>
    <plugin><groupId>org.apache.maven.plugins</groupId><artifactId>maven-compiler-plugin</artifactId><version>3.16.0</version></plugin>
    <plugin><groupId>org.apache.maven.plugins</groupId><artifactId>maven-surefire-plugin</artifactId><version>3.5.5</version></plugin>
  </plugins></build>
</project>
```

将 NameRules 放在 src/main/java，测试放在 src/test/java，再执行 `mvn test`。预期发现两个测试并通过；依赖与插件要事先可用，不能把“没有发现测试”当成验证完成。

## 三 一个测试只证明它实际经过的边界

把输入输出路径画出来，再决定测试需要启动什么：

```mermaid
flowchart LR
    A["HTTP 请求"] --> B["Controller 绑定"]
    B --> C["业务规则"]
    C --> D["数据库或外部系统"]
```

| 测试实际经过什么 | 能证明什么 | 仍需另证什么 |
| --- | --- | --- |
| 直接调用 NameRules | 名称规则 | HTTP 绑定、SQL、事务 |
| MockMvc 调用 Controller | MVC 映射与转换等选定配置 | 真实网络、未包含的安全链或数据库 |
| 真实数据库写入并读取 | SQL、约束和所用事务行为 | 远端服务、全部生产负载 |
| 真实 HTTP 调本地模拟服务 | 实际请求与响应解析 | 生产服务全部业务行为 |

完整范围取决于配置。名称叫“集成测试”并不会自动覆盖所有系统。

## 四 替身控制依赖，让规则测试更确定

替身代替某个外部边界，提供我们需要的输入。先定义一个目录查询接口和使用它的业务类：

```java
interface NameCatalog {
    boolean exists(String name);
}
class NameChecker {
    private final NameCatalog catalog;
    NameChecker(NameCatalog catalog) { this.catalog = catalog; }
    String requireAvailable(String raw) {
        String name = NameRules.normalize(raw);
        if (catalog.exists(name)) {
            throw new IllegalStateException("名称已存在");
        }
        return name;
    }
}
```

测试中自己提供一个最小替身，以下语句放在测试方法内：

```java
NameCatalog catalog = name -> "ODS".equals(name);
NameChecker checker = new NameChecker(catalog);
assertThrows(IllegalStateException.class, () -> checker.requireAvailable(" ODS "));
assertEquals("ADS", checker.requireAvailable(" ADS "));
```

它证明：名称先规范化、存在时拒绝、不存在时返回有效名称。它没有证明真实查询是否带租户条件，也没有证明并发创建一定唯一。

Mock 工具可以配置返回值和核对交互，但不应把 NameChecker 本身替换掉，再宣称已验证它的规则。先用手写替身理解边界，再按项目需要使用 Mockito 等工具。

## 五 集成测试检查真实转换和提交

### 1. HTTP 绑定需要经过 MVC

普通方法调用不会执行路径匹配和参数绑定。下面用一个独立的最小 MVC 测试工程，验证“路径字符串能否转成 Long”。它与第二节的纯 JUnit 工程分开，不需要把两份 POM 拼在一起，也不需要启动 03 的 HTTP 工程。

完整文件结构：

```text
examples/mvc-test/
├── pom.xml
└── src/test/java/study/test/EchoControllerTest.java
```

[完整 POM](/assets/11-测试与质量保障/examples/mvc-test/pom.xml)固定 Java 25、Spring Boot 3.5.16 依赖管理。web 提供 MVC 等类型，starter-test 提供 JUnit 和 Spring 测试能力；本节的测试依赖版本由父 POM 管理，不再手动指定前面纯 JUnit 工程的 6.1.3。

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.16</version>
    </parent>
    <groupId>study</groupId>
    <artifactId>mvc-test</artifactId>
    <version>1.0-SNAPSHOT</version>
    <properties>
        <java.version>25</java.version>
    </properties>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>
</project>
```

[EchoControllerTest.java](/assets/11-测试与质量保障/examples/mvc-test/src/test/java/study/test/EchoControllerTest.java) 是完整测试类，包含被测 Controller 和全部 import：

```java
package study.test;

import org.junit.jupiter.api.Test;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.setup.MockMvcBuilders;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

class EchoControllerTest {
    @RestController
    public static class EchoController {
        @GetMapping("/echo/{id}")
        public String echo(@PathVariable("id") Long id) {
            return id.toString();
        }
    }

    @Test
    void acceptsNumericId() throws Exception {
        MockMvc mvc = MockMvcBuilders.standaloneSetup(new EchoController()).build();
        mvc.perform(get("/echo/12"))
                .andExpect(status().isOk())
                .andExpect(content().string("12"));
    }

    @Test
    void rejectsNonNumericId() throws Exception {
        MockMvc mvc = MockMvcBuilders.standaloneSetup(new EchoController()).build();
        mvc.perform(get("/echo/abc"))
                .andExpect(status().isBadRequest());
    }
}
```

先看被测类型：路径 `/echo/{id}` 的 id 要转为 Long，合法输入返回编号文本。再看两个测试：standaloneSetup 创建 MVC 测试环境，perform 发起模拟请求，andExpect 核对响应。

| 输入 | 预期结果 | 证明什么 |
| --- | --- | --- |
| /echo/12 | 200，响应体为 12 | 路径匹配、参数转换及响应写入经过 MVC |
| /echo/abc | 400 | 无法转成 Long 的参数在业务方法正常执行前被拒绝 |

在这个独立工程目录执行：

```bash
cd ./11-测试与质量保障/examples/mvc-test
mvn test
```

预期发现两个测试并通过。运行使用兼容 JDK 和 Maven，依赖与插件从本地缓存或所配置仓库取得。

standaloneSetup 在测试进程内验证 MVC，不监听真实 HTTP 端口，也不会自动加载公司网关或完整安全链。本节仅完成源码、依赖配置和 XML 的静态核对，尚未执行 Maven 测试。

### 2. 数据库规则需要真实数据库证据

若规则要求“项目内名称唯一”，测试应先建好对应唯一约束，再执行两个相同项目与名称的插入，观察第二次被拒绝。跨项目同名应按规则允许。

验收需要最终表数据与约束错误，不能只验证 Mapper 被调用。事务测试还要观察真实提交边界，避免测试外层统一回滚掩盖业务方法缺少事务的问题。

## 六 契约测试验证调用双方的约定

契约不只有字段名，也包括字段类型、空值、状态码和错误语义。以下样本说明大整数 ID 的约定：

```json
{"id":"9007199254740993","name":"ODS"}
```

| 变更 | 需要观察的兼容问题 |
| --- | --- |
| id 从字符串变数字 | 前端可能丢失整数精度 |
| 新增可选 description | 旧调用方应仍能读取旧字段 |
| name 从非空变为 null | 原调用方是否能处理 |
| 错误从非 2xx 改为 200 加业务码 | 调用方是否仍能识别失败 |

最小做法是保存真实请求响应样本，并让提供方与消费方分别核对约定；团队需要自动协作时再采用 Pact 等工具。只比较一份本地手写 JSON，不能证明线上双方都遵守它。

## 七 故障与并发测试先控制发生顺序

普通 sleep 只能等待，不能证明两个步骤恰好按预期交错。并发问题需要同步屏障、锁或可控制的替身确定关键顺序，再检查最终状态。

以“提交后响应丢失”为例：

| 故障点 | 测试要保留什么 | 不能直接下的结论 |
| --- | --- | --- |
| 数据库提交前抛错 | 最终数据、异常、事务边界 | 有异常就一定回滚 |
| 提交后丢弃响应 | 已提交记录、客户端超时 | 客户端超时就没有创建 |
| 重投同一消息 | 消费去重记录与业务数据 | 日志只出现一次就一定幂等 |

并发与跨服务测试分别依赖 07、09 的实现，先通过它们的最小实验，再将故障加入业务流程。

## 八 综合案例 名称可用性检查

现在把规则、业务协调和可控依赖组合：NameRules 负责名称格式，NameChecker 负责查询后的决定，NameCatalog 是依赖边界。

[examples/RuleCheck.java](/assets/11-测试与质量保障/examples/RuleCheck.java) 提供无外部框架的完整校验，覆盖正常值、空名称、已有名称和可用名称。在章节目录运行：

```bash
mkdir -p /tmp/study-11-classes
javac --release 25 -encoding UTF-8 -d /tmp/study-11-classes examples/*.java
java -cp /tmp/study-11-classes RuleCheck
```

以上主线命令需要 JDK 25。预期输出 `RuleCheck: PASS (trim, blank, duplicate, available)`。

| 证据 | 可以说明 |
| --- | --- |
| 正常输入返回 ODS | 规范化生效 |
| 空名称抛指定异常 | 规则拒绝生效 |
| 替身确认 ODS 已存在后被拒绝 | 业务分支生效 |
| ADS 返回为可用 | 非冲突分支生效 |

随后再把目录查询换成真实数据库实现，为 SQL、租户与并发规则补集成测试。不能把这四项结果扩大成“创建功能已经在生产可用”。

## 九 练习与验收

1. 故意删掉 trim，让原测试失败；恢复实现后用同一断言确认修复。
2. 对空字符串、全空格、null、中文和较长名称列预期，再决定哪些属于本规则、哪些要补业务要求。
3. 使用真实测试数据库验证唯一约束，并保留最终行数；这项随 05、06 完成。
4. 给旧接口增加可选筛选参数，保留旧请求样本并比较新旧结果与错误。

验收时为每个测试写一句“证明什么、尚未经过什么边界”。覆盖率可辅助发现遗漏，不替代业务与故障场景。

## 参考资料与验证范围

- **中文主读**：[廖雪峰单元测试](https://liaoxuefeng.com/books/java/unit-test/index.html)：断言、Fixture、异常与参数化测试，先理解验证行为的方法。
- **现代 Java 补充**：[Dev.java](https://dev.java/learn/)：类、接口、异常与 Lambda 背景；JUnit 的具体版本及构建要求查官方资料。
- **测试框架核对**：[JUnit 6.1.3](https://docs.junit.org/6.1.3/overview.html)与 [Maven 构建支持](https://docs.junit.org/6.1.3/running-tests/build-support.html)：本章纯 JUnit 工程固定 JUnit 6.1.3、Surefire 3.5.5、Java 25。
- **集成测试核对**：[Spring 6.2 MockMvc](https://docs.spring.io/spring-framework/reference/6.2/testing/mockmvc.html)与 [Boot 3.5 测试支持](https://docs.spring.io/spring-boot/3.5/reference/testing/index.html)：MVC 工程的测试依赖由 Boot 3.5.16 管理，不手动叠加前面纯 JUnit 工程的版本。
- **按需补充**：[Mockito 官方入口](https://site.mockito.org/)与 [Pact 文档](https://docs.pact.io/)；Java 25 的实际客户端/工具版本需核对兼容性。
- **Java 8 兼容核查**：[JUnit 5.10.2 文档](https://docs.junit.org/5.10.2/user-guide/)用于对应旧工程，JUnit 6 不能在 Java 8 上运行。

已完成的运行验证仅覆盖 Java 8 目标的纯 Java 综合校验，四种结果通过。新的 Java 25 编译命令、JUnit 6.1.3 与 Boot 3.5.16 组合只做静态核对；当前没有 JDK 25，尚未执行新版构建、MockMvc、数据库或并发集成测试。
